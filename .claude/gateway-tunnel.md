# Gateway and tunnel (`cmd/gateway`, `internal/gateway`, `internal/tunnel`, `internal/agent/netns`)

Lets a task container reach **private services in the customer's network** without the task having general network access. Back to [README](README.md). Flow summary: [architecture](architecture.md#tunnel-task-reaches-the-customers-private-services).

## Gateway (`cmd/gateway`, `internal/gateway/*`)
- A customer creates a gateway in the portal and gets a token + install command. The gateway **dials out** to the coordinator relay (QUIC) and publishes named services (`LAZYCAKE_SERVICES`, e.g. `files=127.0.0.1:8080`). Env: `LAZYCAKE_COORDINATOR_ADDR`, `LAZYCAKE_TOKEN`, `LAZYCAKE_GATEWAY_ID`, `LAZYCAKE_GRPC_ADDR`, `LAZYCAKE_SERVICES`, `LAZYCAKE_GATEWAY_KEY_PATH` (Noise private key file; mount a volume so the key survives container recreation — the server's gateway mounts `/opt/lazycake/gateway-noise.key`), `LAZYCAKE_MAX_MBPS` (optional bandwidth cap in whole Mbps, one `listener.NewBandwidthLimiter` shared by every forwarded connection, both directions; unset/0 = unlimited; **reported to the coordinator in `Hello` at every connect** (`helloMessage` in `cmd/gateway/run.go`), stored in `gateways.max_mbps` and shown on the gateway card and page as "N Mbps" / "No limit" / "Not reported" for a gateway that predates it; the limit is still set only on the container, the dashboard cannot change it), `LAZYCAKE_DEV`. Run as a container with `--restart=always --network=host` (`deploy/Dockerfile --target gateway`).
- `listener` terminates the inner Noise session per stream, reads which service the container wants, and forwards **only to services in its published list**; everything else is refused. It also answers the portal's connection test (per-service reachability; older gateways without it show grey).
- `reporter.go`: coalesces byte reports **per task+service and flushes every 5 s** with a `connections` count (one DB transaction per connection once starved the coordinator — never go back). `run.go` `hello` calls `GatewayService.Hello` with the version after connecting to the relay (an old coordinator answers "unimplemented"; logged at debug, harmless).
- **Deleting a gateway** (portal DELETE, see [portal-api](portal-api.md)): the relay closes its connection with `quic.CodeGatewayRevoked` (2), and refuses any later connection from that gateway id with the same code, checked *before* the token (the token is revoked too, which alone would look like a plain auth failure). Submit, dispatch, `ReportBytes` and `Hello` also refuse an archived gateway. On code 2 the gateway (`cmd/gateway/run.go`) stops retrying, writes `deleted` (its gateway id) next to its key file, and goes **dormant**: it idles, forwards nothing and never dials again, and a container restart reads the marker and stays dormant. It deliberately does not exit: `--restart=always` would just restart it. LazyCake cannot remove the container from the customer's machine (no access, by design), so the dashboard shows `podman rm -f lazycake-gateway && podman volume rm lazycake-gateway-data` after a delete. Gateways older than v0.4.2 do not know code 2: they keep retrying and keep being refused (harmless, backoff 30 s).
- Config/constraints in `internal/gateway/config`.

## Transport (`internal/tunnel`)
- `noise` — Noise_IK between the agent's proxy and the gateway (static keys; the gateway pubkey is in `Dispatch.targets[].noise_pubkey`). The private key never leaves the agent/gateway, so the relay (which terminates QUIC TLS) cannot read task traffic.
- `quic` — outer transport relayed by the coordinator: `relay.go` pumps bytes between an agent stream and a gateway stream, reading only the small frame header (`frame.go`: length-prefixed strings saying which gateway and task the stream is for); `client.go` dial helpers for agent/gateway; `tls.go`; `probe.go` connectivity probe. Relay counts bytes (can only prove a claim too high; its count includes encryption overhead).
- Coordinator side wiring: `internal/coordinator/relay` adapter.

## Agent-side proxy (`internal/agent/netns`)
For a task with targets the container runs `--network=none`. `target.go`/`proxy.go` enter the container's network namespace and run: a stub DNS server (`dns.go`) answering only declared hostnames, each on its own loopback IP (`bind.go`); a TCP listener per target (`serve.go`) that dials through QUIC+Noise to the right gateway; `egress.go` enforces the task's egress byte cap (reason `egress_exceeded`); `fds.go` handles namespace file descriptors (Linux-only). Unlisted hosts have no route at all. The agent counts bytes in both directions and reports them in `TaskFinished`; a shared rate limiter enforces the machine's network offer.

## Caveats
- Containers started for tunnel tests need the in-container tools to exist; network tests use `testdata/netns-spike.sh` ideas and `internal/e2e/tunnel_isolation_test.go`.
- Gateways and agents must be updated by their owners (pull + recreate); the dashboard shows "Update available".
- Gateway container recreation keeps its identity only if its Noise key is on a mounted volume.

## Relay TLS (v0.4.26)
The relay serves the coordinator's real certificate and clients verify it (see [https](https.md)); only loopback/`LAZYCAKE_COORDINATOR_TLS=0` setups still skip verification. `Relay.TLSConfig` supplies the certificate (nil = the old throwaway self-signed one, used by tests and local development). `clientTLSConfig(addr)` in `tls.go` is the dialer's config (`internal/transport.QUICConfig`).

## Agent relay link (v0.4.15)
`internal/agent/netns/relaylink.go`: per task, `relayLink` dials the relay once, retrying the first dial (4 attempts, 500 ms apart), and if the QUIC connection dies it redials once (single-flight) and retries the stream, instead of every stream failing for the rest of the task (the load test logged ~33,000 "opening relayed stream: timeout" from one dead connection). Tests: `relaylink_test.go`.
