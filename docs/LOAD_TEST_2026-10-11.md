# Production load test, 2026-10-11

One run against the production coordinator (1 vCPU, 458 MB RAM, about 1.6 GB free disk) after the database was wiped and reseeded, with two **new**
agents and two **new** gateways (v0.4.8 agents, v0.4.12 gateways): the PC (offered 8 cores / 6 GB, 100 Mbps) and the VM (4 cores / 7 GB, 1 Gbps),
a small-file gateway on the server and a 50 MB-file gateway on the VM. `tools/loadtest/loadtest.py`: 50 minutes of submissions, then up to 12 minutes
of draining.

## Result
- **912 submitted: 855 succeeded, 41 failed, 16 cancelled, none left unfinished.** (The tool stopped with 847 succeeded and the eight 8-core benchmarks
  still queued or running; all eight succeeded afterwards.)
- **The 41 failures are the deliberate ones, plus one:** 11 non-zero exits, 10 wall-clock timeouts (`wall_timeout`), 16 out-of-memory (12 reported
  `exited`, 4 `oom`: the known two-ways reporting), 3 nonexistent images (`error`). 16 cancelled sleepers (`stopped`).
- **One unexpected failure** (`mixed_max`, 5 s, `error`, exit -1, on the VM): the VM agent could not open its relay connection (`dialing relay at
  <server>:7444: timeout: no recent network activity`). It then logged about 33,000 `opening relayed stream` timeouts between about 17:54 and 17:57 UTC.
  The relay (QUIC over UDP) from the VM to the coordinator stalled for a few minutes while the server was at its busiest; it recovered by itself.
  **Open:** a task whose tunnel cannot be reached at start fails as `error` with no output; nothing retries it.
- **Both machines stayed at trust 1.0**, no task was fenced. Work split: PC 545 tasks (26,289 core-seconds), VM 361 (9,755).
- **Gateways:** about 73,000 connections through each; 7.2 GB served (6.7 GB through the VM's 50 MB downloads).
- **Coordinator:** memory peaked at 53 MB, load average 3.7 on one vCPU, free disk never below 1.55 GB; the database ended at 28 MB (55,000 log lines).
- **Rejections: 267** `task rejected` ("does not fit free capacity") in the whole run, about a quarter of all dispatches when busy (see below).

## Found
1. **The scheduler kept dispatching to nodes it had just filled.** Free capacity was only learned from the agent's next report and one task was placed per
   node per second, so the agent refused about 27% of dispatches ("does not fit free capacity"), each costing a 30-second cool-down. Fixed in v0.4.14: each
   dispatch is subtracted from the node's free capacity at once and a node is filled within the tick while tasks fit (`scheduler.reserveFree`, `fillNode`).
2. **The Overview counted tasks from the newest 200 only.** With a backlog the 200 newest were all queued, so it read "0 running, nothing finished".
   Fixed in v0.4.14: `/customer/tasks/summary` counts every task (and gateway pages use it too).
3. **Big tasks starve.** Waiting time in the queue (median): 4-core benchmarks 31 minutes, 8-core benchmarks 42 minutes, against 5 to 9 minutes for
   the small ones. A task is placed on a node only while the node has all its cores free, and the oldest task that *fits* goes first, so a steady stream of
   small tasks keeps a node's free cores below what a big task needs. No 4-core task ran on the 4-core VM in the whole run (19 ran on the PC); 8-core tasks
   can only ever run on the PC (8 offered cores) and waited longest. **Open:** reserve capacity for the oldest waiting big task (drain a node for it) or
   age tasks so they are not overtaken forever.
4. **Reserved is not used.** Cores are reserved by what a task asked for, not by what it burns: at one point the PC had 8 of 8 cores reserved while its
   tasks used 5.0, and the VM 3.5 of 4 reserved for 1.0 used. By design; the dashboard graphs show use, which looks like spare room.

## Notes
- `podman stats` shows `0B / 0B` for the gateway and agent containers: they run with `--network=host`, which that command cannot measure. The traffic is in
  the dashboard (Live bandwidth).
- The tool's report field `db_errors` was misnamed: it is the number of tasks created in the last 3 hours. Now `tasks_created_last_3h`.
- The owner's PC carried the 8 offered cores for an hour: load average 13 on 12 CPUs, memory 74% used. Offer less if the PC is also in use.
