# Production load test, 2026-10-07

Five runs against the production coordinator (1 vCPU, 458 MB RAM, 2 GB free disk) with two real machines: a 12-core PC and a
4-core VM. The first four runs each found a real bug; the fifth passed.

## Bugs found and fixed
| Run | What happened | Root cause | Fix (release) |
|---|---|---|---|
| 1 | After 27 tasks nothing was dispatched; 600 queued, an empty log | Both machines were banned (trust below 0.2) for ordinary work: spec drift compared each task with the average of the machine's first five tasks (any mix of short and long work looked like lying), and byte divergence blamed the relay's encryption overhead on the agent. A ban was forever (no tasks, so no way to earn trust back; canaries off) and silent. | Drift per workload and only for normal exits; relay can only prove a claim too high; trust heals 0.2/hour; bans are logged (v0.3.8) |
| 2 | The PC banned again within 10 minutes | Six sub-second "hello" tasks (0.02-0.3 s of start-up jitter) looked like a 10x slowdown | Ignore tasks under 10 normalised seconds for drift (v0.3.9) |
| 3 | The PC fenced 10 tasks and was banned | Every connection a task opened caused its own gateway report and database transaction; hundreds of tiny connections per second starved heartbeats on the small coordinator, a lease expired, tasks were fenced and counted as abandonment | The gateway batches reports: one per task and service every 5 s with an exact connection count (v0.3.10) |
| 4 | The VM was dispatched tasks but started none | The agent pulled the image before every task, even when cached; Docker Hub's anonymous allowance for the VM's address ran out, and failed pulls kept capacity reserved | Skip the registry for a cached digest-pinned image (v0.3.11) |

Also: an agent installed without a restart policy did not come back after a reboot (fixed in the install command, v0.3.10), and the new
offer check (reject an offer bigger than the machine) refused to start the VM's agent when its free disk dipped just under the 55 GB it
offered (the offer was lowered to 50 GB).

## Run 5 (passed): 59 minutes, 866 tasks
- **866 submitted: 808 succeeded, 44 failed, 14 cancelled; 0 unexpected failures.** The 44 failures are exactly the deliberate ones:
  11 non-zero exits, 11 wall-clock timeouts (reported as `wall_timeout`), 4 nonexistent images (cleanly `error`), 18 out-of-memory.
  The 14 cancellations were the cancelled sleepers (`stopped`).
- **Both machines stayed at trust 1.0** (up from 0.5 by clean completions). No task was fenced.
- **Work split:** the PC ran 536 tasks (29,196 core-seconds, about 70% of its 12 cores), the VM 272 (9,476 core-seconds, about 68% of its 4).
- **Network:** 238,000+ connections through the two gateways, 9.7 GB served through the VM's gateway.
- **Coordinator:** memory peaked at 55 MB (cap 150 MB), load average peaked at 4.6 on one vCPU during the network-heavy stretch and
  recovered, free disk never fell below 1.88 GB; the database was 26 MB afterwards (35,000 log lines, 4,000 usage samples).
- **Queue:** up to 300 in flight on purpose; median queue wait for a benchmark was about 10 minutes at the peak backlog; it drained within
  about six minutes of the last submission.

## Still open (found, not fixed)
1. **357 "task rejected" events:** agents never send capacity reports, so the coordinator dispatches optimistically and the agent's own ledger
   rejects what doesn't fit; each rejection costs a cooldown. It self-corrects but wastes time. Agents should report free capacity.
2. **Out-of-memory is reported two ways** for the same behaviour: 9 as `oom`, 9 as `exited` with code 255 (the program died on a failed
   allocation before the kernel killed it).
3. **27 error-level "metering task finished: meter not found"** lines for tasks that never started (a nonexistent image): harmless noise.
4. **The offer's disk check uses free space,** so a machine that worked yesterday can fail to start when a few MB of unrelated files appear.
5. **Docker Hub pulls are anonymous by default.** A machine that really has to pull many different images will still hit the allowance.
6. Failed tasks of every kind are "clean completions" for trust (+0.01), which is right, but see the load-test finding that a customer's
   deliberate failures were also what first pushed a machine toward a ban through other signals; those signals are now fixed.
